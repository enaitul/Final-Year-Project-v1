1. WHAT IS THIS PROJECT?
================================================================================

   This is an automated testing framework for MySQL databases.

   It takes 300 pre-written SQL test cases from a CSV file, runs each one
   against a live MySQL database, records what happened (the database's
   actual response), and then validates whether the results are correct.

   The project works in two phases:

   PHASE 1 (First Run):
       - Execute all 300 test cases → Save responses → Validate them →
         If correct, save as the "Standard Baseline" (the golden reference).

   PHASE 2 (Future Runs):
       - Execute all 300 test cases → Save responses → Compare against
         the Standard Baseline → Report any regressions or differences.

4. THE TEST CASES (300testcases.csv)
================================================================================

   The CSV file contains 300 test cases covering 100 MySQL features.

   Each row has these columns:
   ┌────────────────┬─────────────────────────────────────────────────┐
   │ Column         │ What it contains                                │
   ├────────────────┼─────────────────────────────────────────────────┤
   │ Test_Case_ID   │ Unique ID like TC001, TC002 ... TC300           │
   │ Feature_ID     │ Feature being tested (F001 to F100)             │
   │ Feature_Name   │ Human-readable name (e.g., "CREATE DATABASE")   │
   │ Test_Type      │ Positive, Negative, or Edge                     │
   │ Test_Description│ What this test does in plain English            │
   │ Preconditions  │ Setup SQL that must run BEFORE the test query   │
   │ SQL_Query      │ The actual SQL statement to execute             │
   │ Expected_Result│ What should happen if the query works correctly │
   │ Expected_Error │ What error is expected (for negative tests)     │
   │ Risk_Level     │ Low / Medium / Critical                         │
   └────────────────┴─────────────────────────────────────────────────┘

   Test Type Breakdown:
       Positive tests : 100  (SQL that SHOULD succeed)
       Negative tests :  98  (SQL that SHOULD fail with an error)
       Edge tests     : 102  (Boundary/unusual conditions)

   Features covered (100 features, F001 to F100):
       F001–F003  : CREATE/DROP/USE DATABASE
       F004       : SHOW DATABASES
       F005–F010  : CREATE/ALTER/RENAME/DROP TABLE
       F011–F020  : INSERT operations (single, multi, NULL, violations)
       F021–F030  : UPDATE operations (single, multi, WHERE, violations)
       F031–F040  : DELETE operations (single, multi, WHERE, cascades)
       F041–F055  : SELECT, WHERE, AND/OR/NOT, DISTINCT, BETWEEN, etc.
       F056–F060  : Aggregate functions (COUNT, SUM, AVG, MIN/MAX, GROUP BY)
       F061–F070  : JOINs (INNER, LEFT, RIGHT, CROSS, SELF, multi-table)
       F071–F080  : Subqueries, EXISTS, UNION, CTEs
       F081–F086  : Constraints (PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL)
       F087–F090  : Functions (String, Numeric, Date/Time, JSON)
       F091–F096  : Transactions (BEGIN, COMMIT, ROLLBACK, SAVEPOINT)
       F097–F100  : Indexes, Views, Stored Procedures, Triggers


5. THE PYTHON FILES — DETAILED EXPLANATION
================================================================================


   ─────────────────────────────────────────────────────────────────────
   FILE 1: test_runner.py  (The Main Program)
   ─────────────────────────────────────────────────────────────────────

   This is the main entry point. You run this to execute all 300 tests.

   Command:    python executor/test_runner.py

   WHAT IT DOES (step by step):

       1. Connects to MySQL using the credentials in DB_CONFIG
       2. Loads all 300 test cases from the CSV file
       3. For each test case:
          a. Reads the SQL query and test metadata from the CSV row
          b. Runs any setup/fixture SQL from the Preconditions column
          c. Determines what the test expects (success or error)
          d. Executes the actual SQL query against MySQL
          e. Captures what MySQL returned (rows, affected count, or error)
          f. Compares expectation vs reality to decide PASS or FAIL
          g. Records the result
       4. Saves all results to a response file (response_1.txt, response_2.txt, etc.)
       5. Prints a summary (total/passed/failed/pass rate)

   KEY FUNCTIONS:

   ┌──────────────────────────┬──────────────────────────────────────────┐
   │ Function                 │ What it does                             │
   ├──────────────────────────┼──────────────────────────────────────────┤
   │ connect_database()       │ Opens connection to MySQL server         │
   │ load_test_cases()        │ Reads the 300testcases.csv into memory   │
   │                          │                                          │
   │ determine_expected_      │ Reads the CSV row and figures out        │
   │   status(row)            │ whether the test expects SUCCESS or      │
   │                          │ ERROR. Uses keywords in Expected_Result  │
   │                          │ and Test_Type to decide.                 │
   │                          │                                          │
   │ extract_setup_sql(text)  │ Extracts the "Setup:" SQL from the      │
   │                          │ Preconditions column of the CSV.         │
   │                          │                                          │
   │ split_setup_statements   │ Splits multiple SQL statements while     │
   │   (setup_sql)            │ keeping stored procedures intact.        │
   │                          │                                          │
   │ run_setup(cursor,        │ Runs the setup/fixture SQL before        │
   │   connection, row)       │ the actual test query.                   │
   │                          │                                          │
   │ format_query_result      │ Formats SELECT results into a readable   │
   │   (cursor, rows)         │ ASCII table with column names.           │
   │                          │                                          │
   │ execute_test(connection, │ THE CORE FUNCTION. Executes one test     │
   │   row)                   │ case and returns a result dictionary     │
   │                          │ with status, actual result, errors, etc. │
   │                          │                                          │
   │ print_test_result(result)│ Displays one test result on screen.      │
   │                          │                                          │
   │ get_next_response_file   │ Finds the next sequential number for     │
   │   (report_dir)           │ the response file name.                  │
   │                          │                                          │
   │ save_response_notepad    │ Writes all results to a response file    │
   │   (results)              │ in a structured text format.             │
   │                          │                                          │
   │ print_summary            │ Prints final pass/fail statistics.       │
   │   (results_df)           │                                          │
   │                          │                                          │
   │ main()                   │ Orchestrates everything above.           │
   └──────────────────────────┴──────────────────────────────────────────┘

   HOW PASS/FAIL IS DECIDED:

       For POSITIVE tests (SQL that should succeed):
           - If SQL executes without error → PASS
           - If SQL throws an error       → FAIL

       For NEGATIVE tests (SQL that should fail):
           - If SQL throws an error       → PASS  (error was expected!)
           - If SQL executes successfully  → FAIL  (should have failed!)

       For EDGE tests:
           - Determined by reading the Expected_Result text in the CSV.
           - Some edge tests expect success, some expect errors.

   RESPONSE FILE FORMAT (what response_1.txt looks like):

       ======================================================================
       Test Case ID: TC001
       Test Type: Positive
       Execution Status: PASS
       Query Executed: CREATE DATABASE ai_testing_scratch_c1;
       Database Response: Query executed successfully. Rows affected: 1
       Query Execution Time: 0.009369 seconds
       ======================================================================

   ─────────────────────────────────────────────────────────────────────

   ─────────────────────────────────────────────────────────────────────

          IF YES (Future Runs):
              → Compares the new response against the baseline
              → Reports regressions and discrepancies

       4. Saves a validation report to response_validation_report.txt
       5. Saves a workflow explanation to how_response_validation_works.txt

6. COMPLETE WORKFLOW — HOW TO USE THE PROJECT
================================================================================

   STEP 0: ONE-TIME DATABASE SETUP
   ──────────────────────────────────────────────────
   Import the database schema into MySQL:

       mysql -u root -p < ai_testing_test.sql

   This creates the "ai_testing_test" database with 4 empty tables.


   STEP 1: RUN THE TEST RUNNER
   ──────────────────────────────────────────────────
   Execute all 300 test cases:

       python executor/test_runner.py

   This will:
   ✓ Connect to MySQL
   ✓ Run all 300 SQL queries one by one
   ✓ Record every response from the database
   ✓ Save results to reports/response_1.txt (or response_2.txt, etc.)
   ✓ Print a pass/fail summary


   STEP 2: VALIDATE AND CREATE BASELINE
   ──────────────────────────────────────────────────
   Validate the response file:

       python executor/validate_and_convert.py

   FIRST TIME (no standard file exists):
   ✓ Minutely validates all 300 test cases in the response file
   ✓ If validation passes, creates standard_test_results.txt
   ✓ The standard file includes side-by-side Expected vs Actual comparisons
   ✓ This becomes the "golden reference" for all future runs

   FUTURE TIMES (standard file already exists):
   ✓ Minutely validates the new response file
   ✓ Compares every test case against the standard baseline
   ✓ Reports any regressions (tests that PASSED before but FAIL now)
   ✓ Reports any output discrepancies (different database responses)
   ✓ Saves report to response_validation_report.txt

8. OUTPUT FILES EXPLAINED

   FILE: response_N.txt (N = 1, 2, 3, ...)
   ─────────────────────────────────────────
   Generated by: test_runner.py
   Contains: Raw database responses for all 300 test cases.
   Naming: Sequential numbering makes it easy to identify which is latest.
   Purpose: This is the raw output of a test execution run.

   Generated by: validate_and_convert.py (on first run only)

       - Full test metadata (ID, Feature, Type, Status)

       - How many test cases were valid/invalid
       - Missing or duplicate test cases
       - Regressions (PASS → FAIL)
       - Output discrepancies
       - Overall verdict (PASS/FAIL)
   Purpose: Quick summary to know if the latest run is correct.

   FILE: how_response_validation_works.txt
   ─────────────────────────────────────────
   Generated by: validate_and_convert.py

   Purpose: Reference documentation.


9. KEY DESIGN DECISIONS
================================================================================

   1. SEQUENTIAL RESPONSE FILES (response_1, response_2, response_3...)
      Instead of timestamps, we use simple sequential numbers.
      This makes it immediately obvious which file is the latest.

   2. TWO-PHASE APPROACH (Baseline then Compare)
      Phase 1 establishes what "correct" looks like.
      Phase 2 checks if anything has changed or broken.
      This is a standard "regression testing" approach.

   3. SIDE-BY-SIDE COMPARISON
      The standard file shows Expected Output and Database Output in
      aligned columns, making it very easy to visually verify correctness.

   4. MINUTE VALIDATION
      Every field of every test case is checked — not just pass/fail.
      This catches formatting issues, missing data, wrong test types, etc.

   5. SETUP/FIXTURE SQL
      Each test case can have precondition SQL (like creating a table
      before testing a DROP TABLE query). The test runner extracts and
      runs this automatically before the actual test query.

   6. POSITIVE/NEGATIVE/EDGE CLASSIFICATION
      - Positive: Normal operations that should succeed
      - Negative: Invalid operations that should fail with a proper error
      - Edge: Boundary conditions and unusual scenarios
