1. EXECUTIVE SUMMARY & OBJECTIVES
--------------------------------------------------------------------------------
In the baseline system, 1,500 test cases are executed across 4 worker processes
(375 cases per group). Rather than subdividing the existing 1,500 test cases into
smaller slices, this phase INCREASES the total number of test cases proportionally
as we scale the number of Agentic AIs:

  • 4 Agents & 4 Groups : 1,500 Test Cases  (375 cases/group across 4 DBs)
  • 6 Agents & 6 Groups : 2,250 Test Cases  (+750 new cases across 6 DBs)
  • 8 Agents & 8 Groups : 3,000 Test Cases  (+1,500 new cases across 8 DBs)

Key Architectural Directives:
1. Tool-Enhanced Agentic AI Multitaskers:
   - Each Agentic AI is an autonomous, tool-equipped worker launched directly
     from inside the Python orchestration program.
   - Each agent operates with specialized tools: query execution, dynamic schema
     introspection, automated privilege/error remediation (e.g. Error 1419),
     and diagnostic classification.
2. Increasing Test Cases with Zero Inter-Dependency:
   - Each group contains a dedicated 375-case suite with independent fixtures,
     isolated tables, and a dedicated disposable database (ai_testing_group1
     through ai_testing_group8).
   - Absolute isolation: zero cross-group queries, zero shared state, zero lock contention.
3. Execution Cycle Improvement & Saturation Point Analysis:
   - Under this weak-scaling model (workload scales with agent count), an ideal
     system completes 1,500, 2,250, and 3,000 cases in approximately the SAME
     cycle time, achieving linear throughput growth (tests/second).
   - Record cycle time and throughput across 4 -> 6 -> 8 agents to pinpoint the
     hardware Saturation Point (CPU core limits, I/O saturation, MySQL connection
     limits, and thread contention).

4. SATURATION POINT DETERMINATION PROTOCOL
================================================================================
1. Objective: Determine at what point adding more parallel Agentic AI workers ceases
   to provide linear throughput gains or starts increasing execution cycle latency.
2. Performance Formulae:
   - Cycle Time (T)        : Time from orchestrator launch to completion of all agents.
   - Throughput (Q)        : Total Test Cases / Cycle Time (cases/second).
   - Weak Scaling Efficiency: (Cycle Time for 4 Agents / Cycle Time for N Agents) * 100%.
3. Detection Criteria for Saturation:
   - Throughput Plateau    : When Q(8 agents) is approximately equal to or less than Q(6 agents).
   - Cycle Time Inflation  : If cycle time jumps significantly due to CPU core oversubscription
                             (e.g., more active agents than physical CPU cores) or MySQL lock waits.
   - Remediation / Pivot   : When local saturation occurs, Afrin's remote distribution module
                             dispatches surplus agents to remote nodes to restore linear throughput.
